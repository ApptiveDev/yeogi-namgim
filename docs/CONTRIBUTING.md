# 협업 가이드

이 문서는 여기남김 프로젝트의 이슈, 브랜치, 커밋, Pull Request(PR), 코드 리뷰 규칙을 설명합니다.

## 협업 흐름

1. 이슈를 생성합니다.
2. 최신 `main`에서 작업 브랜치를 생성합니다.
3. 작업 내용을 커밋하고 원격 저장소에 푸시합니다.
4. `main`을 대상으로 PR을 생성합니다.
5. 필요한 경우 리뷰를 진행하고 수정 사항을 반영합니다.
6. `Squash and merge`로 병합하고 작업 브랜치를 삭제합니다.

## 작업 타입과 영역

### 작업 타입

| 타입 | 설명 |
| --- | --- |
| `feat` | 새로운 기능 또는 사용자 경험 개선 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가 및 수정 |
| `style` | 동작 변경 없는 코드 포맷 수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `test` | 테스트 추가 및 수정 |
| `chore` | 설정, 빌드, 의존성 및 기타 관리 작업 |

### 작업 영역

| 영역 | 설명 |
| --- | --- |
| `fe` | 프론트엔드 작업 |
| `be` | 백엔드 작업 |
| `common` | 공통 설정, 문서, GitHub 템플릿 및 저장소 관리 |

이슈와 PR에는 작업 타입과 영역에 해당하는 라벨을 각각 붙입니다.

- 프론트엔드 기능 구현: `feat`, `fe`
- 백엔드 버그 수정: `fix`, `be`
- 공통 문서 수정: `docs`, `common`
- 프론트엔드와 백엔드를 함께 수정한 기능: `feat`, `fe`, `be`

## 이슈

### 작성 기준

- 작업은 이슈 생성으로 시작합니다.
- 하나의 이슈에는 하나의 작업 목적을 담습니다.
- 담당자를 지정하고 작업 타입과 영역 라벨을 붙입니다.
- 진행 상황에 따라 체크리스트를 갱신합니다.
- 완료가 확인된 항목만 체크합니다.

### 제목

```text
[영역] 타입: 작업 요약
```

영역은 `FE`, `BE`, `COMMON`으로 작성하고, 작업 요약은 한글로 작성합니다. 프론트엔드와 백엔드를 함께 수정하는 작업은 `[FE/BE]`로 표기합니다.

```text
[FE] feat: 로그인 페이지 구현
[BE] fix: 토큰 만료 처리 수정
[COMMON] docs: 협업 가이드 추가
[FE/BE] feat: 로그인 기능 연동
```

### 본문

```markdown
## 작업 목적

작업이 필요한 이유를 작성합니다.

## 구현 범위

- [ ] 구현할 항목

## 완료 조건

- [ ] 작업 완료를 판단할 수 있는 조건

## 참고 자료

관련 문서, 화면, 이슈 등의 링크를 작성합니다.
```

구현하거나 확인해야 할 항목은 체크리스트로 작성합니다. 참고 자료가 없으면 해당 항목은 생략할 수 있습니다.

## 브랜치

### 현재 운영 기준

- 현재는 `main`과 이슈별 작업 브랜치로 협업합니다.
- `main`은 배포 가능한 안정된 상태로 유지합니다.
- `main`에 직접 커밋하지 않고 작업 브랜치에서 개발합니다.
- 작업 브랜치는 최신 `main`에서 이슈 단위로 생성합니다.
- PR의 대상 브랜치는 `main`으로 설정합니다.
- 배포는 `main`을 기준으로 진행합니다.
- 배포 후 수정도 `main`에서 작업 브랜치를 생성하여 진행합니다.
- 머지 완료 후 작업 브랜치를 삭제합니다.

### 추후 `develop` 도입

개발 코드와 배포 버전을 분리할 필요가 생기면 팀원과 협의하여 `develop`을 도입합니다.

1. 최신 `main`에서 `develop`을 생성합니다.
2. 이후 작업 브랜치는 최신 `develop`에서 생성합니다.
3. 작업 완료 후 PR을 통해 `develop`에 병합합니다.
4. 개발과 검증이 완료되면 `develop`에서 `main`으로 PR을 생성하여 병합합니다.
5. `main`을 기준으로 배포합니다.

도입 이후 `develop`은 계속 유지하며 다음 개발 작업의 기준으로 사용합니다. 전환 시 이 문서의 협업 흐름, 브랜치 생성 예시, PR 대상 및 머지 규칙도 함께 변경합니다.

### 브랜치 이름

```text
타입/영역/#이슈번호-작업내용
```

작업 내용은 영문 소문자와 하이픈으로 작성합니다. 프론트엔드와 백엔드를 함께 수정하는 작업은 영역을 `fe-be`로 표기합니다.

```text
feat/fe/#12-login-page
fix/be/#18-token-refresh
docs/common/#21-contributing-guide
feat/fe-be/#24-login-integration
refactor/be/#30-api-response
```

### 작업 예시

최신 `main`에서 작업 브랜치를 생성합니다.

```bash
git switch main
git pull --ff-only origin main
git switch -c 'feat/fe/#12-login-page'
```

작업 후 원격 저장소에 푸시합니다.

```bash
git push -u origin 'feat/fe/#12-login-page'
```

## 커밋

### 메시지 형식

```text
타입: 작업 요약

본문 — 필요한 경우
```

```text
feat: 로그인 페이지 구현
fix: 토큰 만료 처리 수정
docs: 협업 가이드 추가
refactor: 사용자 서비스 구조 개선
```

### 작성 기준

- 정해진 작업 타입을 접두사로 사용합니다.
- 커밋 제목에는 작업 영역을 별도로 표기하지 않습니다.
- 제목은 변경 내용을 알 수 있도록 한글로 간결하게 작성합니다.
- 제목 끝에는 마침표를 붙이지 않습니다.
- 상세한 변경 이유나 설명이 필요하면 본문에 작성합니다.
- 하나의 커밋에는 하나의 변경 의도를 담습니다.
- 서로 밀접하게 관련된 변경은 하나의 커밋으로 묶습니다.
- 파일 개수나 폴더보다 변경 목적을 기준으로 커밋을 나눕니다.

## Pull Request

### 작성 기준

- 작업 브랜치에서 `main`을 대상으로 생성합니다.
- 하나의 PR에는 하나의 작업 목적을 담고, 리뷰하기 좋은 크기로 유지합니다.
- 관련 이슈를 연결하고 작업 타입과 영역 라벨을 붙입니다.
- 이슈와 PR에는 같은 기준으로 라벨을 붙입니다.
- 작업 중 피드백이 필요하면 Draft PR을 활용합니다.

### 제목

```text
타입: 작업 요약 (#이슈번호)
```

```text
feat: 로그인 페이지 구현 (#12)
fix: 토큰 만료 처리 수정 (#18)
docs: 협업 가이드 추가 (#21)
```

### 본문

```markdown
## 작업 내용

- 주요 변경 내용을 작성합니다.

## 테스트 및 확인

- 확인한 방법과 결과를 작성합니다.
- 확인하지 못한 항목이 있다면 이유를 작성합니다.

## 관련 이슈

Closes #이슈번호

## 참고 사항

리뷰어가 알아야 할 내용이나 화면을 첨부합니다.
```

- PR이 이슈의 완료 조건을 모두 충족하면 `Closes #이슈번호`로 연결합니다.
- 일부 작업만 포함하거나 참고용으로 연결할 때는 `Refs #이슈번호`를 사용합니다.
- 참고 사항이 없으면 해당 항목은 생략할 수 있습니다.

### 머지 전 체크리스트

- [ ] 대상 브랜치가 `main`인지 확인했습니다.
- [ ] 관련 이슈를 연결하고 라벨을 붙였습니다.
- [ ] 작업에 필요한 테스트나 동작 확인을 진행하고 결과를 작성했습니다.
- [ ] 불필요한 로그와 임시 파일을 제거했습니다.
- [ ] 변경에 필요한 문서를 함께 수정했습니다.
- [ ] 최신 `main`과의 충돌을 해결했습니다.
- [ ] 리뷰에서 필수 수정 사항이 제기된 경우 해결했습니다.

### 머지 기준

- 리뷰가 필요한 경우 관련 팀원에게 요청합니다.
- 리뷰 없이도 작성자가 확인 후 머지할 수 있습니다.
- 리뷰에서 필수 수정 사항이 제기되면 해결한 뒤 머지합니다.
- 충돌은 작업자가 해결합니다.
- `Squash and merge`로 `main`에 병합합니다.
- Squash 커밋 제목은 PR 제목을 기준으로 커밋 컨벤션에 맞게 작성합니다.
- 머지 완료 후 원격 작업 브랜치를 삭제합니다.

## 코드 리뷰

코드 리뷰는 코드의 품질을 높이고, 변경 내용과 개발 지식을 팀원끼리 공유하기 위해 필요한 경우 진행합니다.

### 진행 절차

1. 작성자는 변경 목적과 확인 결과를 PR에 작성하고, 필요한 경우 리뷰를 요청합니다.
2. 리뷰어는 변경 내용을 확인하고 의견을 남깁니다.
3. 작성자는 피드백을 반영하거나 자신의 판단과 근거를 설명합니다.
4. 필수 수정 사항을 해결한 뒤 머지합니다. 리뷰를 진행하지 않는 경우 작성자가 확인 후 머지할 수 있습니다.

### 리뷰 상태

| 상태 | 사용 기준 |
| --- | --- |
| `Comment` | 질문이나 제안을 남길 때 |
| `Request Changes` | 머지 전에 수정이 필요한 문제가 있을 때 |
| `Approve` | 변경 내용을 확인했고 머지해도 괜찮다고 판단할 때 |

### 검토 항목

- **동작 정확성**: 의도한 기능과 요구사항을 충족하는지
- **오류 처리**: 예외 상황과 경계 조건을 적절히 처리하는지
- **가독성**: 이름과 코드 흐름을 이해하기 쉬운지
- **복잡성**: 같은 동작을 더 간단하게 표현할 수 있는지
- **재사용성**: 기존 코드와 중복되는 부분이 있는지
- **구조**: 역할과 책임이 적절히 분리되어 있는지
- **성능**: 불필요한 연산이나 자원 사용이 있는지
- **검증**: 변경에 필요한 테스트나 확인이 이루어졌는지

### 피드백 방법

- 작성자를 평가하지 않고 코드와 변경 내용을 중심으로 이야기합니다.
- 문제의 위치와 이유를 구체적으로 설명합니다.
- 가능한 경우 개선 방향이나 예시를 함께 제안합니다.
- 필수 수정과 선택적인 제안을 구분합니다.
- 이해되지 않는 부분은 질문합니다.
- 좋은 구현이나 도움이 된 부분도 공유합니다.
