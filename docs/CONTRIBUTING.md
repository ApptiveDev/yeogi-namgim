이 문서는 여기남김 프로젝트의 이슈, 브랜치, 커밋, Pull Request(PR), 코드 리뷰 규칙을 설명합니다.

## 협업 흐름

1. 이슈를 생성합니다.
2. 최신 `main`에서 작업 브랜치를 생성합니다.
3. 작업 내용을 커밋하고 원격 저장소에 푸시합니다.
4. `main`을 대상으로 PR을 생성합니다.
5. PR 생성 직후 Codex 자동 리뷰와 GitHub Actions 검사를 병렬로 실행합니다.
6. PR 작성자는 자동 리뷰와 검사 결과를 확인하고 문제를 수정합니다. 새 커밋을 푸시하면 자동 검사를 다시 실행합니다.
7. 다른 팀원이 코드를 직접 검토한 뒤 `Approve`합니다.
8. GitHub Actions 통과와 팀원 1명 이상의 `Approve`를 확인한 뒤 PR 작성자가 `Squash and merge`로 병합합니다.
9. 머지한 작업 브랜치를 삭제합니다.

## 작업 타입과 영역

### 작업 타입

| 타입 | 설명 |
| --- | --- |
| `feat` | 새로운 기능 또는 사용자 경험 개선 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가 및 수정 |
| `style` | 동작 변경 없는 코드 포맷 수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `test` | 테스트 추가 및 수정 |
| `chore` | 설정, 빌드, 의존성 및 기타 관리 작업 |

### 작업 영역

| 영역 | 설명 |
| --- | --- |
| `fe` | 프론트엔드 작업 |
| `be` | 백엔드 작업 |
| `common` | 공통 설정, 문서, GitHub 템플릿 및 저장소 관리 |

이슈와 PR에는 작업 타입과 영역에 해당하는 라벨을 각각 붙입니다.

- 프론트엔드 기능 구현: `feat`, `fe`
- 백엔드 버그 수정: `fix`, `be`
- 공통 문서 수정: `docs`, `common`
- 프론트엔드와 백엔드를 함께 수정한 기능: `feat`, `fe`, `be`

## 이슈

### 작성 기준

- 작업은 이슈 생성으로 시작합니다.
- 하나의 이슈에는 하나의 작업 목적을 담습니다.
- 담당자를 지정하고 작업 타입과 영역 라벨을 붙입니다.
- 진행 상황에 따라 체크리스트를 갱신합니다.
- 완료가 확인된 항목만 체크합니다.

### 제목

```text
[영역] 타입: 작업 요약
```

영역은 `FE`, `BE`, `COMMON`으로 작성하고, 작업 요약은 한글로 작성합니다. 프론트엔드와 백엔드를 함께 수정하는 작업은 `[FE/BE]`로 표기합니다.

```text
[FE] feat: 로그인 페이지 구현
[BE] fix: 토큰 만료 처리 수정
[COMMON] docs: 협업 가이드 추가
[FE/BE] feat: 로그인 기능 연동
```

### 본문

```markdown
## 작업 목적

작업이 필요한 이유를 작성합니다.

## 구현 범위

- [ ] 구현할 항목

## 완료 조건

- [ ] 작업 완료를 판단할 수 있는 조건

## 참고 자료

관련 문서, 화면, 이슈 등의 링크를 작성합니다.
```

구현하거나 확인해야 할 항목은 체크리스트로 작성합니다. 참고 자료가 없으면 해당 항목은 생략할 수 있습니다.

## 브랜치

### 현재 운영 기준

- 별도의 `develop` 브랜치 없이 `main`과 이슈별 작업 브랜치로 협업합니다.
- `main`은 배포 가능한 안정된 상태로 유지합니다.
- `main`에 직접 커밋하지 않고 작업 브랜치에서 개발합니다.
- 작업 브랜치는 최신 `main`에서 이슈 단위로 생성합니다.
- 기능, 수정, 문서 작업의 PR 대상 브랜치는 `main`으로 설정합니다.
- 배포는 `main`을 기준으로 진행합니다.
- 머지 완료 후 작업 브랜치를 삭제합니다.

### 브랜치 이름

```text
타입/영역/#이슈번호-작업내용
```

작업 내용은 영문 소문자와 하이픈으로 작성합니다. 프론트엔드와 백엔드를 함께 수정하는 작업은 영역을 `fe-be`로 표기합니다.

```text
feat/fe/#12-login-page
fix/be/#18-token-refresh
docs/common/#21-contributing-guide
feat/fe-be/#24-login-integration
refactor/be/#30-api-response
```

### 작업 예시

최신 `main`에서 작업 브랜치를 생성합니다.

```bash
git switch main
git pull --ff-only origin main
git switch -c 'feat/fe/#12-login-page'
```

작업 후 원격 저장소에 푸시합니다.

```bash
git push -u origin 'feat/fe/#12-login-page'
```

## 커밋

### 메시지 형식

```text
타입: 작업 요약

본문 — 필요한 경우
```

```text
feat: 로그인 페이지 구현
fix: 토큰 만료 처리 수정
docs: 협업 가이드 추가
refactor: 사용자 서비스 구조 개선
```

### 작성 기준

- 정해진 작업 타입을 접두사로 사용합니다.
- 커밋 제목에는 작업 영역을 별도로 표기하지 않습니다.
- 제목은 변경 내용을 알 수 있도록 한글로 간결하게 작성합니다.
- 제목 끝에는 마침표를 붙이지 않습니다.
- 상세한 변경 이유나 설명이 필요하면 본문에 작성합니다.
- 하나의 커밋에는 하나의 변경 의도를 담습니다.
- 서로 밀접하게 관련된 변경은 하나의 커밋으로 묶습니다.
- 파일 개수나 폴더보다 변경 목적을 기준으로 커밋을 나눕니다.

## Pull Request

### 작성 기준

- 작업 브랜치에서 `main`을 대상으로 생성합니다.
- 하나의 PR에는 하나의 작업 목적을 담고, 리뷰하기 좋은 크기로 유지합니다.
- 관련 이슈를 연결하고 작업 타입과 영역 라벨을 붙입니다.
- 이슈와 PR에는 같은 기준으로 라벨을 붙입니다.
- 작업 중 피드백이 필요하면 Draft PR을 활용합니다.

### 제목

```text
타입: 작업 요약
```

```text
feat: 로그인 페이지 구현
fix: 토큰 만료 처리 수정
docs: 협업 가이드 추가
```

PR 제목에는 이슈번호를 표기하지 않고, 관련 이슈는 본문에서 연결합니다. 브랜치 이름에는 이슈번호를 유지합니다.

### 본문

```markdown
## 작업 내용

- 주요 변경 내용을 작성합니다.

## 테스트 및 확인

- 확인한 방법과 결과를 작성합니다.
- 확인하지 못한 항목이 있다면 이유를 작성합니다.

## 관련 이슈

Closes #이슈번호

## 참고 사항

리뷰어가 알아야 할 내용이나 화면을 첨부합니다.
```

- PR이 이슈의 완료 조건을 모두 충족하면 `Closes #이슈번호`로 연결합니다.
- 일부 작업만 포함하거나 참고용으로 연결할 때는 `Refs #이슈번호`를 사용합니다.
- 참고 사항이 없으면 해당 항목은 생략할 수 있습니다.

### 머지 전 체크리스트

- [ ] 대상 브랜치가 `main`인지 확인했습니다.
- [ ] 관련 이슈를 연결하고 라벨을 붙였습니다.
- [ ] 변경에 필요한 테스트 코드를 작성하고 로컬 테스트 결과를 작성했습니다.
- [ ] Codex 자동 리뷰 결과를 확인하고 필수 수정 사항을 해결했습니다.
- [ ] GitHub Actions의 빌드 및 테스트 검사가 통과했습니다.
- [ ] 다른 팀원 1명 이상이 코드를 검토한 뒤 `Approve`했습니다.
- [ ] 불필요한 로그와 임시 파일을 제거했습니다.
- [ ] 변경에 필요한 문서를 함께 수정했습니다.
- [ ] 최신 `main`과의 충돌을 해결했습니다.
- [ ] 리뷰에서 필수 수정 사항이 제기된 경우 해결했습니다.

### 머지 기준

- Codex 자동 리뷰와 GitHub Actions 검사가 완료되기 전에는 머지하지 않습니다.
- GitHub Actions의 필수 검사가 모두 통과해야 합니다.
- PR 작성자가 아닌 팀원 1명 이상이 코드를 직접 검토하고 `Approve`해야 합니다.
- Codex 또는 팀원 리뷰에서 필수 수정 사항이 제기되면 해결한 뒤 머지합니다.
- 충돌은 작업자가 해결합니다.
- PR 작성자가 `Squash and merge`로 `main`에 병합합니다.
- Squash 커밋 제목은 PR 제목을 기준으로 커밋 컨벤션에 맞게 작성합니다.
- 머지 완료 후 원격 작업 브랜치를 삭제합니다.

## 자동 검사와 테스트

PR을 생성하면 Codex 자동 리뷰와 GitHub Actions 검사를 병렬로 실행합니다. 이 검사는 머지 이후가 아니라 PR 단계에서 변경 사항을 검증하고 머지 가능 여부를 판단하기 위한 필수 절차입니다.

| 담당 | 역할 |
| --- | --- |
| Codex | 버그, 보안, 예외 처리, 로직을 중심으로 자동 코드 리뷰 |
| GitHub Actions | Gradle 빌드와 JUnit 테스트 자동 실행 |
| 다른 팀원 | 변경 코드를 직접 검토하고 `Approve` 또는 수정 요청 |
| PR 작성자 | 자동 검사와 리뷰 결과를 반영하고 최종 머지 |

### 실행 시점

- PR을 생성하거나 Draft PR을 Ready for review로 전환하면 자동 리뷰와 검사를 실행합니다.
- PR 브랜치에 새 커밋을 푸시하면 GitHub Actions 검사를 다시 실행합니다.
- `main`에 머지한 이후에도 검사를 실행할 수 있지만, 머지를 허용하는 필수 검사는 PR 단계에서 통과해야 합니다.
- 자동 리뷰와 테스트는 사람의 코드 리뷰를 대신하지 않습니다.

### 백엔드 테스트 작성 기준

- 백엔드 기능을 추가하거나 동작을 변경하면 해당 변경을 검증하는 JUnit 테스트를 함께 작성합니다.
- 정상 동작뿐 아니라 주요 실패 상황, 예외 처리, 경계 조건도 테스트합니다.
- 버그를 수정할 때는 같은 문제가 다시 발생하지 않도록 재현 테스트를 추가합니다.
- 테스트하기 어려운 구조라면 테스트를 생략하기보다 역할과 의존성을 분리하여 테스트 가능한 구조로 개선합니다.
- 문서나 주석처럼 실행 동작에 영향을 주지 않는 변경은 테스트를 생략할 수 있으며, PR의 `테스트 및 확인`에 사유를 작성합니다.

백엔드 테스트는 로컬에서 다음 명령으로 확인합니다.

```bash
cd backend
./gradlew test
./gradlew build
```

## 코드 리뷰

코드 리뷰는 코드의 품질을 높이고, 변경 내용과 개발 지식을 팀원끼리 공유하기 위한 필수 절차입니다.

### 진행 절차

1. PR 생성 직후 Codex가 변경 사항을 자동으로 검토합니다.
2. GitHub Actions가 Gradle 빌드와 JUnit 테스트를 실행합니다.
3. 작성자는 자동 리뷰와 검사 결과를 확인하고 수정 사항을 반영합니다.
4. 다른 팀원은 변경 코드를 직접 검토한 뒤 의견을 남기고 `Approve` 또는 `Request Changes`를 선택합니다.
5. 작성자는 필수 수정 사항을 해결하고 GitHub Actions 통과와 팀원 1명 이상의 `Approve`를 확인한 뒤 머지합니다.

### 리뷰 상태

| 상태 | 사용 기준 |
| --- | --- |
| `Comment` | 질문이나 제안을 남길 때 |
| `Request Changes` | 머지 전에 수정이 필요한 문제가 있을 때 |
| `Approve` | 변경 코드를 직접 검토했고 머지해도 괜찮다고 판단할 때 |

### 검토 항목

- **동작 정확성**: 의도한 기능과 요구사항을 충족하는지
- **오류 처리**: 예외 상황과 경계 조건을 적절히 처리하는지
- **가독성**: 이름과 코드 흐름을 이해하기 쉬운지
- **복잡성**: 같은 동작을 더 간단하게 표현할 수 있는지
- **재사용성**: 기존 코드와 중복되는 부분이 있는지
- **구조**: 역할과 책임이 적절히 분리되어 있는지
- **성능**: 불필요한 연산이나 자원 사용이 있는지
- **검증**: 변경에 필요한 테스트나 확인이 이루어졌는지

### 피드백 방법

- 작성자를 평가하지 않고 코드와 변경 내용을 중심으로 이야기합니다.
- 문제의 위치와 이유를 구체적으로 설명합니다.
- 가능한 경우 개선 방향이나 예시를 함께 제안합니다.
- 필수 수정과 선택적인 제안을 구분합니다.
- 이해되지 않는 부분은 질문합니다.
- 좋은 구현이나 도움이 된 부분도 공유합니다.
