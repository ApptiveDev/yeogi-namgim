# 백엔드 작업 지침

이 문서는 `backend/`에서 작업하는 AI 에이전트에게 적용한다. 저장소 루트의 `AGENTS.md`가 있다면 함께 따르고, 협업 절차는 [`docs/CONTRIBUTING.md`](../docs/CONTRIBUTING.md)를 따른다. 사용자가 지정한 작업 범위 밖의 코드는 수정하지 않는다.

## 작업 전에 확인할 자료

1. 요청과 연결된 이슈, 현재 `main`의 코드, 관련 열린 PR을 확인한다. 계획 문서의 체크 표시만으로 구현 완료를 판단하지 않는다.
2. [`BACKEND_API_CONTRACT.md`](../docs/BACKEND_API_CONTRACT.md)를 읽어 인증, 공통 응답, 데이터·담당 경계를 확인한다.
3. 지도·위치·열람·친구 공개 범위를 다룬다면 [`FINAL_POLICY_AND_AUDIT.md`](../docs/FINAL_POLICY_AND_AUDIT.md)와 [`MEMBER_MAP_API.md`](../docs/MEMBER_MAP_API.md)를 함께 읽는다.
4. 변경할 도메인의 상세 문서를 확인한다: [이메일 인증](../docs/EMAIL_AUTH_API.md), [토큰 세션](../docs/TOKEN_SESSION_API.md), [회원 쪽지](../docs/MEMBER_NOTE_API.md), [친구](../docs/FRIEND_API.md). 다른 `docs/*_API.md` 파일이 추가되었다면 해당 문서도 확인한다.

기존 문서는 작성 당시의 계약을 보존한 부분이 있다. 2026-10-31에 결정한 **회원 전용 요청과 타인 미저장 쪽지 열람 반경 150m**는 [PR #74](https://github.com/ApptiveDev/yeogi-namgim/pull/74)에서 작업 중이므로, PR이 병합되었는지 먼저 확인한다. 오래된 문서의 200m 또는 종료 예정 흐름을 새 기능의 기준으로 복사하지 않는다. 문서·코드·최신 확정 요구가 충돌하면 근거를 확인하고 관련 계약을 함께 정정한다. 미병합 기능을 현재 `main`의 구현으로 표시하지 않는다.

## API를 만들거나 바꿀 때

- 컨트롤러 경로와 DTO만이 아니라 인증·권한, 서비스 판정, 데이터 조회, 오류 응답, 프론트 호출 영향까지 확인한다. 요청에서 받은 사용자 ID만으로 소유권을 결정하지 않는다.
- **새 API**는 관련 도메인의 `docs/*_API.md`에 추가한다. 적절한 도메인 문서가 없다면 `docs/<DOMAIN>_API.md`를 새로 만든다. 경로 하나마다 파일을 만들 필요는 없다.
- **기존 API의 경로·필드·검증·권한·상태 코드·거리·정렬·페이지네이션이 바뀌면** 해당 도메인 문서를 같은 작업에서 갱신한다. 내부 구현만 바뀌어 외부 계약이 같다면 문서 변경이 필요한지 검토하고 PR에 판단 근거를 적는다.
- API 문서에는 최소한 메서드·전체 경로, 인증 조건, 요청·응답 예시, 주요 오류, 권한·위치 경계, 페이지네이션(해당 시), 관련 이슈·PR, 구현 상태를 적는다. 계획과 구현을 구분하고 실제 코드와 테스트로 확인한 내용만 완료로 쓴다.
- [문서 PR #86](https://github.com/ApptiveDev/yeogi-namgim/pull/86)의 `docs/API_CATALOG.md`가 `main`에 병합되었다면 해당 기능의 담당 A/B, 경로, 이슈·PR 상태를 함께 갱신한다. **병합 전 기능을 완료(`[x]`)로 표시하지 않는다.** [추적 이슈 #87](https://github.com/ApptiveDev/yeogi-namgim/issues/87)의 완료 체크는 연결된 작업 PR이 `main`에 병합되어 이슈가 닫힐 때 반영된다.
- API 계약을 바꾸면 관련 프론트 호출부와 다른 백엔드 소비자를 확인한다. 별도 작업이면 필요한 연동 범위와 선행 조건을 PR에 명시한다.

## 구현과 검증

- 기존 `controller`·`dto`·`service`·`repository`·`domain` 경계를 따르고, 공통 인증·접근 판정을 우회하는 임시 코드를 넣지 않는다. 상세·지도·목록에서 공개 범위와 거리 판정이 서로 달라지지 않게 한다.
- DB 스키마 변경은 새로운 Flyway 파일로 추가한다. 이미 적용된 마이그레이션을 수정하지 않고, 병렬 PR의 버전 번호를 확인한다.
- 정상 동작과 함께 인증 실패, 잘못된 입력, 타인 데이터 접근, 공개 범위, 위치·거리 경계, 중복 요청 등 해당 변경에 필요한 JUnit 테스트를 작성한다.
- `backend/README.md`에 따라 PostgreSQL/PostGIS와 환경변수를 준비한 뒤 변경 영역의 테스트와 `./gradlew build`를 실행한다. 실행하지 못한 검사는 이유와 미검증 범위를 PR에 적는다.
- 실제 비밀값·토큰·개인정보를 코드, 문서, 로그, 테스트 결과에 남기지 않는다. 문제가 해결된 뒤 임시 디버그 로그를 제거한다.

## PR에서 확인할 사항

- 변경된 API의 도메인 문서와 필요한 경우 API 목록을 갱신한다. PR 본문에는 변경 계약, 프론트 영향, 테스트 결과, 미구현 범위를 적는다.
- `.github/pull_request_template.md`의 항목은 확인한 것만 체크한다. 백엔드 운영 Java 코드·Flyway 파일이 바뀌었는데 API 문서가 하나도 바뀌지 않으면 `API docs` 자동 검사가 실패한다. 외부 API 계약이 그대로인 내부 수정이라면 PR 본문에 `API_DOCS_NOT_REQUIRED: 구체적인 이유`를 한 줄로 적는다. 이 검사는 **문서 파일의 변경 여부 또는 예외 사유의 존재만 확인**하며 내용의 정확성은 작성자와 리뷰어가 검토한다.
- 문서만 추가했다고 구현 완료로 표시하거나, PR을 병합 없이 닫은 일을 완료로 처리하지 않는다.
